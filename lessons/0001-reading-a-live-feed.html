Lesson 01 · data.gov.sg real-time APIs

Reading a live feed

The weather app's first question is “what's the forecast where I'm standing?” By the end of this ~20-minute lesson you'll have a function that answers it from live government data.

Today's win A tested nearestForecast(json, lat, lng) that you'll paste straight into your Next.js app in Lesson 02.

1 · One base URL, many feeds

Every weather and air feed lives under one base URL. No key is needed to start. “All Data.gov.sg APIs are public and can be accessed without an API key for testing purposes.” API overview

2 · The envelope

Every v2 response is wrapped the same way. Check code, not just the HTTP status. On an error, data is null, and code that reads json.data.items crashes. Both errors below were triggered for real while preparing this lesson. Firing nine calls in a burst got 429 from the 4th call onward. 

{ "code": 0, "errorMsg": "", "data": { … } }        // success
{ "code": 4,  "name": "ERROR_PARAMS",      "data": null, … }  // HTTP 400, bad ?date=
{ "code": 24, "name": "TOO_MANY_REQUESTS", "data": null, … }  // HTTP 429

The 429 is the one you'll meet. Without a key you get 6 real-time calls per 10 seconds, shared by everything your app does (rate limits). A Dev key raises that to 12 and a Prod key to 30. Hold that thought until Lesson 02.

3 · Metadata + readings: the join

The core pattern across every feed is that places and values come in separate arrays, and you join them by name or id. Here is a trimmed live two-hr-forecast response: 

"data": {
  "area_metadata": [
    { "name": "Ang Mo Kio", "label_location": { "latitude": 1.375, "longitude": 103.839 } },
    { "name": "Bedok",      "label_location": { "latitude": 1.321, "longitude": 103.924 } }, …
  ],
  "items": [{                              // a time series: one entry per issue time
    "timestamp": "2026-10-20T13:22:00+08:00",  // SGT, ISO-8601 with offset
    "valid_period": { "start": "…T13:00:00+08:00", "end": "…T15:00:00+08:00", "text": "1.00 pm to 3.00 pm" },
    "forecasts": [ { "area": "Ang Mo Kio", "forecast": "Cloudy" }, … ]
  }]
}

Gotcha: the casing isn't consistent. This feed uses area_metadata / label_location, but psi and pm25 use regionMetadata / labelLocation, and the station feeds use stations + readings[].data[{stationId, value}]. Don't share one parser between feeds. Write a small adapter per feed (Lesson 03).

To find the forecast for a user at (lat, lng), take the latest item, find the nearest area in the metadata, and look up that area's forecast. With no ?date= you normally get just the latest item, but items is still an array. Pass ?date=2026-10-19 and you get the whole day. Don't hard-code items[0].

4 · Lab: build nearestForecast

Write the function below. Run fetches the live feed straight from your browser (the API sends Access-Control-Allow-Origin: *) and checks your answers against a reference. Responses are cached for 60 s, so re-running won't trip the rate limit. Ctrl+Enter runs.

Requirements: (a) throw if json.code !== 0; (b) use the item with the latest timestamp; (c) return { area, forecast, validUntil }, where validUntil is that item's valid_period.end.

5 · Retrieval check

Answer from memory before scrolling up. That effort is what makes it stick. The first click locks in.
